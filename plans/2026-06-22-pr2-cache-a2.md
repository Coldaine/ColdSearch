# PR 2: Search History and Research Memory Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ColdSearch preserves previous executions as inspectable research history, can retrieve relevant prior work, and lets humans or agents compare or reuse it before issuing more provider calls.

**Architecture:** Extend the existing cache, usage logging, generic provider-tool substrate, `FanoutEngine`, and `LocalExecutionBackend` into one useful execution-record path. Do not design a second observability system or a new architecture program. Keep storage cheap, local, and inspectable. Exact-response caching remains a supporting freshness/replay mechanism rather than the operator-facing product concept.

**Tech Stack:** TypeScript, Node.js filesystem APIs, built-in `node:test`, and the existing JSON/JSONL persistence. Add a lightweight local search/index package only if it materially reduces implementation complexity.

---

## Scope

Implement the operator/agent-facing history surface:

- `coldsearch history recent`
- `coldsearch history search <query>`
- `coldsearch history show <execution-id>`
- `coldsearch history show <execution-id> --by-provider`
- raw provider-result inspection where ColdSearch preserved raw output
- cheap local retrieval of related prior searches before deciding whether to make another provider call
- inspection of prior result URLs and whether a page was previously extracted
- comparison of overlapping and provider-unique URLs from already-justified fanout executions

Every meaningful search, extract, crawl, and provider-tool execution should leave a useful record containing:

- original query or URL
- timestamp
- capability and selected provider/tool
- routing decision
- normalized result
- raw provider result where available
- result URLs
- latency
- success or error
- live execution, exact-cache replay, or intentional history-reuse status
- safe key reference already available from usage/provider-tool logging, never the secret value
- run ID when one exists

When fanout or another multi-provider execution already occurs for real work, preserve before merging:

- URLs returned by each provider
- overlapping and provider-unique URLs
- per-provider errors and latency
- merged/reranked output

Do not call extra providers solely to populate those comparisons.

Keep these cache mechanics as supporting implementation work in this PR, not the primary CLI concept:

- `coldsearch cache clear`
- `--freshness <duration>` for exact replay on search, extract, and eligible provider tools
- atomic cache/history writes
- restrictive cache/history directory and file permissions where supported
- explicit crawl-cache policy

Exact response replay remains allowed only for exact keys satisfying freshness policy. Related history is surfaced with age and provenance so the caller or agent can decide whether another live call is warranted; it must not silently replay merely because a cache key or fuzzy match exists.

Do not implement:

- a formal benchmark corpus or provider scoring ontology
- required annotations, usefulness labels, or relevance scores
- paid provider comparison as part of `npm test`, merge gates, default completion checklists, or general PR validation
- extra multi-provider calls whose only purpose is comparison statistics
- daemonized state, cross-process locking, or a remote history backend
- remote execution or batch execution

## Crawl-Cache Decision

Default: record crawl executions in history, but keep exact crawl replay disabled in this PR.

- Crawls can represent broad site snapshots.
- Crawl results are sensitive to site state, depth, and limit.
- History inspection remains useful even when exact replay is unsafe.
- Add crawl replay later only with an explicit TTL and complete request-key inputs if real workloads justify it.

## Success Criteria

- A human or agent can discover previous and related work before issuing another provider call.
- An execution can be inspected as request, normalized result, raw result where available, provenance, timing, live/reuse status, and failure state.
- Real fanout work naturally accumulates inspectable provider-comparison evidence without extra provider calls.
- Previous extraction and result URLs are locally discoverable.
- Exact replay remains explicit and freshness-safe; relevant-history retrieval is preferred over blind replay.
- Cache hygiene supports the history surface without becoming the primary product concept.
- No benchmark corpus, scoring framework, or annotation requirement is introduced.
