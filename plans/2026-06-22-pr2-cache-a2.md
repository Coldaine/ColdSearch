# PR 2: Search History and Research Memory Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Preserve ColdSearch executions as useful local research history so humans and agents can discover and inspect prior work without conflating history with exact-response cache replay.

**Architecture:** Add a durable execution-record path around the existing `LocalExecutionBackend`, `FanoutEngine`, cache, usage logging, and provider-tool substrate. Keep storage local, simple, and inspectable. Exact-response caching remains a separate freshness/replay mechanism. Do not create a second observability architecture or pull PR 5 run-ID work into this PR.

**Core invariant:** history records what ColdSearch did; cache determines whether a prior exact result may be replayed. An approximate history match never suppresses a live provider call automatically.

**Tech Stack:** TypeScript, Node.js filesystem APIs, built-in `node:test`, and existing JSON/JSONL persistence. Add a lightweight local search/index package only if it materially reduces implementation complexity; do not pre-commit to embeddings or vector infrastructure.

---

## Scope

### Execution record

Create one top-level history execution for each invocation of:

- `coldsearch search`
- `coldsearch extract`
- `coldsearch crawl`
- `coldsearch tool call`

A multi-provider fanout is one execution with provider attempts/results beneath it. Do not create one top-level history item per provider leg.

Persist information ColdSearch actually has, including:

- stable execution ID
- timestamp
- command/capability and original query or URL
- relevant ColdSearch request options and provider-specific parameters where available
- routing strategy and requested provider scope
- providers actually attempted
- source: `live` or `cache`
- origin execution ID for exact-cache replay when known
- provider attempts with provider/tool, success/error, timing, and safe key reference where available
- normalized provider results where available
- raw provider detail only where the existing execution path already preserves it
- final normalized or merged result
- result URLs or artifact references
- overall errors and duration
- optional run/agent correlation fields only when another existing path already supplies them; generating/threading run IDs remains PR 5

Do not refactor every normalized adapter solely to capture raw HTTP payloads or reconstruct exact native requests. If raw provider detail was not preserved, history reports it as unavailable.

Raw provider detail and error bodies are provider-supplied content: before persisting, scrub any resolved credential value they contain (provider error responses can echo credentials). If content cannot be scrubbed safely, mark the raw detail unavailable rather than persisting it. A provider error must never turn durable history into a local secret store.

### Persistence failures

A history record is the audit trail that an execution occurred, so silently losing one is worse than a cache miss. When a history write fails (read-only directory, full disk, I/O error), surface an observable, non-secret warning on stderr and in `--json` output metadata instead of swallowing the error the way cache persistence does. The command result itself stays accurate; the warning states that the execution was not recorded in history.

### Cache-hit history

An exact cache hit still creates a new execution-history record because ColdSearch was invoked at that time.

Record:

- the new execution ID and timestamp
- `source = cache`
- zero provider calls
- the originating execution ID when available
- cache age/freshness provenance needed to explain the replay
- the returned normalized result

History survives cache expiry and `cache clear`. Cache TTL and replay-cache deletion must not erase execution history.

### Fanout preservation

`FanoutEngine.search()` already holds provider result partitions before reranking. Preserve those partitions for the history writer rather than discarding them after the merged result is produced.

For an already-justified fanout execution, store:

- each provider's pre-merge normalized result set
- per-provider success/error
- per-provider timing where available
- providers actually used
- final merged/reranked output

Do not call extra providers solely to populate comparison data. Do not add provider grades or relevance scores.

## History Commands

### `coldsearch history recent`

Purpose: answer **what has ColdSearch actually done recently?**

Behavior:

- list top-level executions newest first
- one row/item per ColdSearch invocation, not per provider attempt
- include live, cache-replay, partial-success, and failed executions
- use a bounded default (20) and support `--limit <n>`
- support `--json`

Human-readable entries should contain enough information to recognize the work without opening it:

- timestamp/age
- execution ID
- command/capability
- abbreviated original input
- providers attempted/used
- source (`live` or `cache`)
- outcome (`success`, `partial`, or `failed`)
- result count where meaningful

Expired cache entries must remain discoverable through history.

### `coldsearch history search <query>`

Purpose: answer **have we already researched something like this, and what prior execution contains useful material?**

This command is local-only and must make zero provider calls.

Search prior execution records using, initially:

1. original request/query or URL — strongest match
2. normalized result titles and URLs/domains
3. normalized snippets/content where practical
4. provider/tool metadata

Do not index arbitrary raw provider JSON by default.

Bound the result set: use a bounded default (20 matching executions) and support `--limit <n>` and `--json`, so a common term in a long-lived history cannot produce unbounded output or memory use.

Return matching **executions**, not a flat list of matching individual web results. For each matching execution, expose why it matched, such as:

- matching request/query
- matching result title
- matching result URL/domain
- matching snippet/content
- matching provider/tool metadata

When individual stored results caused the match, include those matching results beneath the execution. Recency may break otherwise similar matches, but do not invent a provider-quality or universal relevance scoring system in this PR.

`history search` surfaces prior work only. It must not automatically reuse it or suppress a requested live search.

### `coldsearch history show <execution-id>`

Purpose: answer **exactly what happened during this execution?**

Show, as available:

1. **Request** — execution ID, timestamp, command, original input, source, duration, outcome.
2. **Routing** — strategy, requested provider scope, providers attempted/used, reranker where relevant.
3. **Cache provenance** — miss/live execution, or exact replay with origin execution, age, and zero provider calls.
4. **Provider attempts** — provider/tool, success/error, timing, result count, safe key reference where available.
5. **Final result** — the normalized/merged output actually returned to the caller.
6. **Errors** — including provider failures that occurred inside an overall successful/partial execution.
7. **Raw detail** — only where that execution path preserved it; otherwise report raw detail as unavailable.

Support `--json`.

### `coldsearch history show <execution-id> --by-provider`

For stored fanout work, show each provider's pre-merge results/errors separately and then the final merged/reranked result.

It may compute simple facts from stored data at display time, such as URL overlap and provider-unique URL counts. It must not:

- call a provider
- rank providers
- declare a provider the winner
- invent relevance judgements

`history compare <id1> <id2>` is a useful follow-on once the core records and show views exist, but it is not required to deliver PR 2.

### `coldsearch history clear --all`

History is durable independently of replay-cache TTL, but it must not be undeletable.

Initial behavior:

- explicitly delete all local execution-history records
- require `--all` so this destructive operation is unambiguous
- report how many records were removed
- leave replay-cache material untouched
- support `--json`

Do not invent automatic history TTL/pruning in this PR without evidence that a particular retention default is useful. A selective `--before`/prune surface can be added later if real history growth warrants it.

## Cache Work Retained In PR 2

History and cache are separate surfaces. Keep the existing cache work rather than deleting it during the history reframe:

- `coldsearch cache stats`
- `coldsearch cache clear`
- `--freshness <duration>` for exact replay on search, extract, and eligible provider-tool results
- atomic cache/history writes
- restrictive cache/history directory and file permissions where supported
- explicit crawl-cache policy

`cache stats` describes replay-cache storage, not research-history counts.

`cache clear` clears replay-cache material only. It must not delete history records.

Exact response replay remains allowed only for exact keys satisfying freshness policy. Related history is never treated as an exact cache hit.

### Provider-tool replay/freshness

Provider-tool calls currently preserve raw results but do not have a general result-cache path. If PR 2 continues to promise `--freshness` for provider-tool results, implement that promise explicitly rather than assuming the normalized cache covers it.

- Define explicit replay eligibility for provider tools whose request shape can produce a stable exact cache key and whose semantics are safe for replay.
- Thread `--freshness` through `tool call` only for those explicitly eligible tools.
- Store eligible provider-tool exact results in the replay cache while still recording every invocation in history.
- Provider tools without an explicit replay-safe key/policy remain history-only and always execute live when invoked.
- Do not infer replay safety merely because a tool is catalogued or synchronous.

### Crawl-cache decision

Record crawl invocations in history, but keep exact crawl replay disabled in this PR.

- Crawls can represent broad site snapshots.
- Results are sensitive to site state, depth, and limit.
- History inspection is useful even when exact replay is unsafe.
- Add crawl replay later only with an explicit TTL and complete request-key inputs if real workloads justify it.

## Explicitly Out Of Scope

Do not implement in PR 2:

- a formal benchmark corpus or provider scoring ontology
- paid provider comparison as routine validation
- required annotations, usefulness labels, tags, or relevance scores
- automatic fuzzy history reuse
- automatic history injection into every normal `search` command
- a `history reuse` command
- migration/import of old exact-cache entries unless implementation inspection demonstrates a trivial compatibility path
- embeddings/vector infrastructure as a requirement
- full raw-response preservation refactors across normalized provider adapters
- generation or propagation of PR 5 run IDs / agent-step correlation
- daemonized state, cross-process locking, or remote history storage
- batch or remote execution

## Success Criteria

- A human or agent can browse recent ColdSearch work and locally find related prior executions.
- `history show` reconstructs what observable work happened during a stored execution.
- Fanout results remain inspectable by provider after reranking.
- Exact cache replay is freshness-controlled and clearly separate from history retrieval.
- Cache maintenance remains available and cannot erase research history.
- Research history has an explicit operator-controlled deletion path independent of cache cleanup.
- Provider-tool freshness/replay is either explicitly supported for replay-safe tools or explicitly unavailable; it is never implied without implementation/tests.
- No benchmark corpus, provider scoring framework, annotation system, migration project, vector-search requirement, or PR 5 trace implementation is introduced.
