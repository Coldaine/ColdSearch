# PR 1: Searchable Cache, Cache Operations, and Cache Hygiene Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the existing exact-result cache into a useful local recent-result memory: searchable, inspectable, logged, and still cheap to maintain. Cache operations and file-write hardening ship in the same PR.

**Architecture:** Extend the existing `CacheStore` and keep cache orchestration above `FanoutEngine` in `LocalExecutionBackend`. Do not add a daemon or remote cache backend in this PR. Prefer a simple local index or painless package over standing up a bespoke caching layer. Keep cache failures non-fatal.

**Tech Stack:** TypeScript, Node.js filesystem APIs, built-in `node:test`, existing JSON file cache layout. Add a lightweight local search/index package only if it materially reduces implementation complexity.

---

## Scope

Implement:

- Searchable cache/recent-result memory over prior search/extract/tool entries
- `coldsearch cache search <query>`
- `coldsearch cache recent`
- `coldsearch cache stats`
- `coldsearch cache clear`
- `--freshness <duration>` for `search` and `extract`
- Cache lookup/search/hit/miss logging with selected prior item references
- Atomic cache writes
- Restrictive cache directory/file permissions where supported
- Explicit crawl-cache decision

Do not implement:

- `coldsearch batch`
- Daemonized cache state
- Cross-process locking
- Remote cache backend
- Fuzzy cache search suppressing provider calls by default

Exact response replay remains allowed only for exact cache keys that satisfy freshness policy. Searchable cache retrieval should surface relevant prior items; it should not silently replace a provider call unless the request is an exact fresh hit.

## Crawl-Cache Decision

Default decision: keep crawl uncached in this PR.

Document this reason:

- Crawls can represent broad site snapshots.
- Crawl results are more sensitive to site state and crawl depth.
- Current repeated-work pressure is on search/extract and batch enrichment.
- Crawl cache can be added later with `crawl_ttl` and `{ limit }` in the key if real workloads justify it.

If the user explicitly asks for crawl cache during this PR, implement it in the same cache layer with:

- `crawl_ttl`
- cache key options `{ limit }`
- the same provider-scope bypass behavior as search/extract
- explicit docs and tests
